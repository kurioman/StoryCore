THE NARRATOR: WHAT IS SENT TO THE AI, AND WHAT HAPPENS AFTER
==========================================================

Code: services/context_builder.py (build), services/turns.py, services/runtime.py, services/turn_analysis.py,
services/extraction.py. In the app, open a story and use the Context Inspector to see exactly what was sent.


1. ONE REQUEST = A SYSTEM PROMPT + RECENT MESSAGES
--------------------------------------------------
context_builder.build() returns:
  system    one text made of "# Title\nbody" sections (below)
  messages  the most recent player/narrator messages that fit
  manifest  token counts per section, what was left out and why, warnings (shown in the Context Inspector)
  secrets   the narrator-only text (so the preview can mask it)
  turn_context  (v0.5, "stable" layout) the per-turn sections, sent at the top of the player's last message
  instructions  system + turn_context (for side requests that send only a system prompt: continuity check)

Layout (v0.5 phase 7.3, setting context_layout):
  stable (default)  STABLE_SECTIONS stay in the system prompt: core, global_note, story_note, avatar (profile only),
                    roles, known, recap, scene_summaries, portrait_tags, music_tags, narration_language. Every other
                    section (player_state, scene, canon, events, facts, lore, secrets, memories, threads, narration
                    rules last) goes at the top of the player's latest message, between TURN_OPEN and TURN_CLOSE. Old
                    messages leave in steps: the oldest message sent is moved forward to the first message after the
                    end of a memory summary (or every 8 messages), when more than the minimum fit. The beginning of the
                    request is then identical for several turns: LM Studio / llama.cpp reuse their prompt cache,
                    DeepSeek and Gemini bill cached input less, and Claude gets cache_control markers (system prompt +
                    the message before the player's turn; AnthropicAdapter and OpenRouter "anthropic/" models). The
                    opening request keeps everything in the system prompt.
  classic           Everything in the system prompt (v1.7 behaviour).
Player side (phase 7.4): the golden Recap button calls POST /player-recap: one request built from the memory layers,
the open threads and the latest messages not yet summarised, written in the story language for the player ("Previously…"
+ "Still pending"); kept in story.settings_json.player_recap and returned again while the head message is the same. The
Journal's "AI memory" tab (MemoryTab.jsx) shows the layers (edit, pin as a fact), the open threads (settle / reopen:
story.settings_json.memory_closed_threads, also hidden from the narrator), the character notes, "Summarise now" and
"Close the chapter here" (also /chapter, alias /chapitre: catch-up with force=True, then every active scene merged into
one chapter, data_json.title). A long story opened after more than 4 hours offers the recap above the message box.

Token use (phase 7.5, services/usage.py): every adapter reports usage in one shape (prompt_tokens, completion_tokens,
cached_tokens, cost) — OpenAI-compatible servers are asked for it in streams too (stream_options.include_usage, dropped
if refused), Ollama (prompt_eval_count), Anthropic (cache read/creation counted in), OpenAI Responses. Narrator replies
keep it in their metadata; side requests (analysis, capture, summaries, recap) are added up in
story.settings_json.usage_side. After each reply usage.calibrate() folds real/estimated prompt size into
settings_json.token_ratio (moving average, 0.6–2.0); the builder divides the budget and the hard limit by it.
GET /stories/{sid}/usage feeds the gauge next to the context meter (UsageMeter.jsx). The scene analysis is skipped
(status "skipped") for a reply under 700 characters with no character named or present, when place and time are
already known and suggested replies are off.

Continuity checks (phase 7.6, services/continuity.py), shown as notices under the reply
(generation_metadata_json.continuity_alerts: {kind, ...}); the reply is never changed:
  repetition     no model call: 5-word phrases found in 2+ of the last 6 narrator replies (merged into runs) and openings
                 used twice; the per-turn section "repetition" asks to vary them (setting anti_repetition).
  dead_speaks    no model call: a character of a witnessed "death" journal event (earlier on the path) speaks in a reply
                 (analysis speakers, else portrait tags / heuristic speaker). Checked after the analysis.
  time_back      no model call: the analysis moves the time of day back by more than 90 minutes on the same day.
  contradiction  the scene analysis also receives up to 8 pinned memories and reports a clear contradiction in its
                 "warnings" (no extra request).
Stepped window, refined: the start of the previous request (story.settings_json.window_starts, written by turns.py) is
kept while it still fits; a forced move goes to a memory boundary leaving the minimum of recent messages, else as far
as the minimum allows (starting on a player message), then the window grows again.

Short lore cards (setting lore_short_cards): a character's lore entries are sent when they come into focus; while
they stay (named in the messages before the last exchange) and have a cast line, the entries are listed as "short
card (already in the scene)" and left out. Pinned lore is always sent.

Sections, in order (key in brackets; [optional] ones are dropped first when space runs out):
   1 core          The world's narrative prompt (pack ai/narrative_system_prompt.md) - or the default prompt for a
                   story without a world - + style preset, tone, pacing, length, agency policy, content preferences,
                   agency rules, and an extra instruction for special turns (opening scene, immersive mode).
   2 global_note   The player's global note (Settings).
   3 story_note    The story's own note (overrides the global note and base lore).
   4 avatar        The protagonist (player's avatar profile).
   4b player_state The player state (stats, inventory...), separate since v0.5 (it changes every turn).
   5 scene         Current place/time/weather/day, characters present and mentioned (with short lore summaries
                   and looks), relationships between them (lore background + values evolved in the story).
   5b roles        Established posts and closed groups: never reassign, never invent a second holder.
   5c known        Characters the protagonist has already met (discoveries).
   5d canon        Kinship, family branches, the gathering under way (class roster...).
   5e group_scene  Who is in the room and who has been quiet (natural attention in group scenes).
   5f encounters   [optional] Up to three established characters plausibly nearby (never a script).
   6 pinned        Pinned memories.
   7 events        [optional] Journal: timeline digest + relevant events.
   7 facts         [optional] Relevant facts and beliefs (who knows what).
   8 lore          [optional] Lore of characters in focus + full-text search hits (up to 6) + pinned lore +
                   approved local canon. About 20 % of the budget; long chunks cut at 2400 characters.
   8b secrets      Narrator-only "hidden" notes of the records in play (never dropped). See 04_LOREPACK.txt.
   9 recap         [optional] Rolling "story so far" recap.
   9a scene_summaries [optional, dropped last] (v0.5) The automatic memory (services/summaries.py), newer than the
                   rolling recap: the story so far (always), then the newest chapters and scenes no longer sent word
                   for word, about 15 % of the budget.
   9b recalled     [optional] (v0.5) Up to 2 merged scenes whose detail matches the recent text (full-text search on
                   names and places).
   9c character_memory [optional] (v0.5) The last 3 memory lines of each character in focus (from the scenes).
   9d threads      [optional] (v0.5) Open threads: promises, debts, quests, mysteries still pending (12 at most).
   9b portrait_tags  The [Name:N] portrait tag rule (worlds only; setting portrait_tags_enabled). See 04_LOREPACK.txt.
  10 narration_rules  Short operational rules placed LAST (small models obey the last instructions best).
Then the recent messages, newest first until the budget is used (at least "recent_messages_min", default 6).
When even that does not fit, optional sections are dropped in this order: lore, encounters, events, facts, recalled,
character_memory, recap, threads, scene_summaries.

Automatic summaries (v0.5, phase 7): memory capture (batch mode, every 3 replies) also returns "scene_summary", 2-5
English sentences about the messages it just read, in the same request (setting scene_summaries_enabled). Anything left
without a summary (capture off or manual, an older game, an empty field) is summarised after a reply by
summaries.catch_up with the story's own model: at most 2 short requests, oldest messages first, chunks of up to 10
messages; with capture off the newest messages wait for 6 of them. A summary covers exact message ids: it is used only
on a path containing all of them, and editing / regenerating / deleting one marks it stale (written again).
Layers (phase 7.2): with 12 active scenes the 8 oldest are merged into a chapter; with 6 chapters the 2 oldest are folded
(with the previous one) into a single "story so far". Merged rows become "superseded" with parent_id, so the active rows
always partition the story and the memory sent stays bounded. A stale row gives its other children back (active).
Each scene also stores, in data_json, one memory line per character ("notes", keyed by lore id or "name:<name>") and
the threads it opened or settled ("threads_opened", "threads_resolved" as keys "<summary id>:<n>"); the prompts show the
open threads as T1, T2... Capture returns them as character_notes / threads_opened / threads_resolved.

Budget: setting context_budget_tokens (default 10 000) or the story's own; never more than the model's window
(model profile context_limit, or Ollama num_ctx) minus the reply size, with a 10 % safety margin. Token counts are
estimates (characters / 4).

Prompt profiles (setting narrator_prompt_profile; default v5_history_hygiene): variants of where the rules go and
whether a short reminder is added after the player's turn; v5 also hides trailing "options menus" of earlier
replies from the model (the saved story is unchanged). Defined in context_builder.PROMPT_PROFILES.


2. WHERE EACH PIECE COMES FROM
------------------------------
  World prompt, premise, lore, posts, facts, gatherings, places, calendar, stats, openings   -> the Lore Pack
  Notes, presets, budget, prompt profile, analysis/memory options                          -> app settings
  Per-story options (model, preset, tone, notes, exclusions, pinned lore, story language)   -> stories.settings_json
  Scene, cast, clock, relationships, stats                                                  -> story_states (versioned)
  Journal, facts, recaps, discoveries                                                       -> memory tables
Story language (v0.5, services/narration_language.py): app setting narration_language (en | fr), overridable per
story (settings_json.narration_language). For French, a "Story language" section is added after the portrait-tag rule,
and "(Write your reply in French.)" after each player turn (not after the opening request). Lore, instructions, portrait
tags, names and the analysis JSON stay in English; suggested replies follow the reply's language on their own.
To change what the narrator is told about a WORLD: edit the pack. To change how the ENGINE talks to every model:
edit context_builder.py (and keep the manifest in sync so the inspector stays truthful).


3. THE OPENING SCENE
--------------------
POST /api/stories/{id}/start uses the starter blueprint chosen in the wizard (stored in stories.settings_json as
starter_blueprint) as the instruction for the first reply (routers/stories.py, "Generate the opening scene").


4. AFTER EACH REPLY
-------------------
main.py -> after_generation(message_id), only for replies that ended normally:
  a. turns.post_process         cheap offline heuristics (speaker, mood)
  a2. portrait_tags.apply       the narrator's [Name:N] tags -> portraits + expressions at once (no extra request);
                                without tags, the speakers found while streaming (live_speakers, see below)
  b. turn_analysis.analyse      ONE small JSON request to a model (ANALYSIS_MAX_TOKENS = 1800):
                                  - speakers and reactions with an expression 1-6 (portraits),
                                  - who is present / left (scene_cast.py),
                                  - three suggested replies in the player's voice (suggestions.py; off by default),
                                  - characters discovered (discovery.py),
                                  - relationship changes with a quoted proof (relationships.py),
                                  - time / place / weather changes with proof (world_state.py).
                                Everything is validated against the reply text; anything unproven is dropped.
                                Setting turn_analysis_mode: always | local_only | off.
  c. extraction (memory capture) by batch (setting event_capture_mode: off | manual | batch | after_each_turn):
                                journal events, facts, recap suggestions, continuity problems, state-change
                                proposals (review queue). Uses the narration model or a separate one
                                (extraction_model_source).
Failures there never touch the reply: the player sees a Retry button.

Hidden notes and the analysis: the analysis and memory capture read the TRANSCRIPT, not the secrets section, so a
secret only enters memory if the narrator actually wrote it into the story.


5. TUNING TIPS
--------------
  - Small local models (7-13B): keep the world prompt short and concrete; prefer facts in pack.json/lore fields over
    long Markdown; keep context_budget_tokens within the model's real context (LM Studio "Context Length").
  - If replies are cut: raise the model profile's max_tokens, or lower it if the model's window is small.
  - If the narrator invents a second ruler / god: add a post or closed group in pack.json.
  - If a character is never met: add places (regulars / likely) or a gathering in pack.json.

PHASE 9 (v0.6): SMALLER REQUESTS
--------------------------------
Measured with the mock narrator after 3 turns (estimated tokens, characters / 4):
                      fixed sections before -> after
  Hero's Chronicle    2430 -> 2147   roles 422 -> 271, portrait tags 142 -> 113, scene 235 -> 205, lore 419 -> 345
  Lumencia Academy    3763 -> 3666   roles 565 -> 409, encounters 146 -> 130; lore now holds real records (see below)
  - Lore records (lore_import.record_text): no id / name (the chunk title has it) / _index_type / source_ids lines; the
    confidence line only when it is not "high"; small blocks of plain values on one line ("appearance: hair: blue;
    eyes: gold"). Importer version 6: every pack is re-imported once at start.
  - Not retrieved as lore any more: the pack's system prompt file and every Markdown file under ai/ or scenarios/ (and
    README.md), and the records of the "scenario" and "source" categories. They were found by the lore search and sent
    again in pieces (the narrator already has its rules whole; openings are used when a story starts).
  - Shorter wording, same rules: established posts (roles.render_block, no [id] and "locked" labels), possible
    encounters, portrait tags, scene consistency lines. The narration rules (final section) are unchanged on purpose:
    they were tuned on live failures of local models.
  Not changed yet, to test with a real model first: the scene analysis system prompt (turn_analysis.RULES, about 1300
  tokens on every turn; with a JSON schema the shape part repeats the schema).

PHASE 9.2-9.4 (v0.6): PLAYABLE WITH A LOCAL MODEL
-------------------------------------------------
Diagnosed on the owner's game (rocinante-12b, LM Studio) and in live tests:
  - "Replayed scene": /continue (CONTINUE_TEMPLATE, now v3) did not forbid repeating; replies could run to 8,000
    tokens and looped; the repetition penalty was sent as "repetition_penalty", which LM Studio ignores.
  - The GGUF had no chat template: LM Studio used "Instruct:/Human:" and the model answered a turn by copying the
    previous reply, then wrote "Human:" and our per-turn context. ChatML set in LM Studio fixed it.
  - 10.4 GB Q6_K_L + 32k f16 cache on a 12 GB card spilled into shared memory (20 s before the first word, 7 tok/s).
    Q4_K_M + 24k context + Q8_0 K/V cache: about 8.6 GB.
Engine changes:
  - services/reply_cleanup.py (called from turns.post_process, setting reply_cleanup, never for the mock narrator):
    paragraphs whose 4-word sequences are 60% already in the last 3 replies (or earlier in the same reply) removed; a
    reply cut by max_tokens trimmed to its last sentence; a trailing options menu dropped; a leaked next turn
    ("\nHuman:", "<|im_start|>", "[Story context for this turn") cut. Tag offsets move with the text; never empties.
  - runtime.story_params: max_tokens capped by the target length (settings_service.REPLY_TOKEN_CAPS: short 380,
    medium 650, long 1050); repeat_penalty 1.08 for local story replies only (never JSON requests).
  - OpenAICompatAdapter: repeat_penalty keeps its name for local servers; local requests get stop sequences
    (LOCAL_STOPS).
  - context_builder: with a known window and no story budget, the budget follows the window up to AUTO_BUDGET_CAP
    (24,000; setting context_budget_auto); lore budget capped at LORE_BUDGET_MAX (1,600). Two narration rules added
    (never repeat earlier replies; never invent a shared past).
  - Narration first (runtime.GenerationManager.side_tasks / stop_side_requests): the post-reply hooks of a story are
    cancelled when its next narration starts; a running scene analysis is marked skipped ("the next reply had
    priority"); capture and summaries catch up on a later turn.
  Tests: app/backend/tests/test_phase9.py.

PORTRAITS WHILE THE REPLY IS WRITTEN (v0.6, "Portraits")
--------------------------------------------------------
Measured before: Rocinante 12B almost never wrote [Name:N], so the portrait waited for the scene analysis (reply ends
at ~4 s, portrait at ~10 s in the simulation; tagged replies showed it only at the very end, never while streaming).
  - services/live_speakers.py: LiveSpeakers follows the streamed text (runtime.GenerationManager._follow_speakers, after
    every delta). Per paragraph: a narrator tag wins; else the name next to the quotes ("« ... », dit Lily",
    '"...," Lily said', "Lily sourit : « ... »", French + English speech verbs); else, once the paragraph is finished,
    the one character named in its narration or (« ... », dit-elle) in the paragraph before. The protagonist's lines
    are never attributed ('"...," you call out', "« ... », répondez-vous", 'You smile: "..."'). No model call.
    Each change -> stream event {"type": "portraits", "beats": [...]} (also replayed after "snapshot"); stored with the
    reply as generation_metadata_json.live_speakers. Off in immersive interleaving (marker filter active).
  - portrait_tags.apply: without narrator tags, the detected speakers become the reply's portraits at once (beats
    source "detected"; the expression shown is kept). turn_analysis: detected beats give way to the analysis' speakers;
    a detected line of a confirmed speaker keeps its portrait. Narrator tags still win over the analysis.
  - History tags: generation_metadata_json.portrait_tags (source tag | detected | analysis; the analysis writes them
    with portrait_tags.from_beats) are put back into earlier replies by portrait_tags.retag; replies analysed before
    0.6 get theirs from their analysis row (portrait_tags.history_fallback). Small models copy the transcript: in the
    live test Rocinante wrote [Lily:2] itself two turns later.
  - Per-turn note (context_builder, after the OOC reminder, before the language note which stays last):
    "(Portraits: ... e.g. [Lily:2] « Bonjour. » ...)" with the last speaker or someone present as the example.
  - Setting portrait_tags_enabled (Settings > Memory, "Ask the AI to mark who speaks"): off = no rule, no note, no tags
    in the history (tokens saved); live detection and the analysis still show the portraits.
  - Screen: StoryPage keeps the live beats per message (shown while streaming, and until the saved presentation
    arrives); lib/portraits.usePreloadPortraits loads the 6 expressions (full + thumb) of everyone in the scene.
  Tests: app/backend/tests/test_portraits_live.py.
